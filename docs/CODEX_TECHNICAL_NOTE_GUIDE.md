# Codex 技术文档录入规范

这份文档用于保证 Codex 在不同聊天窗口中新增、迁移或重写技术文档时，仍然遵循同一套内容标准、标签体系、视觉语言和安全边界。它是 `AGENTS.md` 的技术笔记专项补充；两者冲突时，以仓库根目录的 `AGENTS.md` 和用户当次明确要求为准。

## 1. 开始前必须读取的内容

修改技术文档前，依次完整读取：

1. 仓库根目录 `AGENTS.md`。
2. 本文档 `docs/CODEX_TECHNICAL_NOTE_GUIDE.md`。
3. `src/content.config.ts`，确认 `notes` 集合的当前字段和校验规则。
4. 至少一篇内容类型相近的现有笔记，以及 `src/layouts/ContentLayout.astro`、`src/components/cards/NoteRow.astro` 和 `src/pages/notes/index.astro`。
5. 用户提供的原始笔记、数据手册、代码、接线图和错误日志。文件必须完整读取，不能只根据文件名或开头生成内容。

先通过只读检查确认工作树状态，保留与本次任务无关的用户修改。

## 2. 文件位置与自动发现

- 正文放在 `src/content/notes/<slug>.md` 或 `.mdx`。
- slug 使用小写 ASCII kebab-case，例如 `esp8266-at-mqtt-guide`。
- 普通技术文档优先使用 Markdown；只有确实需要 Astro 表达式、自定义组件或动态资源路径时才使用 MDX。
- 文档图片放在 `public/images/notes/<slug>/`。技术笔记主页的公共视觉放在 `public/images/notes/`。
- 默认通过 `npm run new:note -- <slug>` 创建骨架，再根据资料完整改写；不得保留模板占位文字。
- 新文档必须被内容集合自动发现、自动生成详情路由，并自动进入笔记列表。不得在页面组件中硬编码单篇文章。

## 3. 先校验事实，再补充解释

用户笔记可以作为实践记录，但不能自动视为完整、最新或完全正确的技术规范。

1. 保留用户真实遇到的问题、接线方式、调试过程和有效结论。
2. 对供电、电平、引脚、协议、波特率、启动模式、版本限制、安全要求等关键事实，优先使用芯片厂商、框架官方文档、标准或原始论文核对。
3. 软件版本、云平台命令和硬件规格存在变化可能时，必须查询当前官方资料；不要仅凭记忆补写。
4. 原始资料与官方规范冲突时，以经过核实的事实修正文档，并解释原记录为什么容易造成误解。
5. 无法验证的行为要写明测试环境、版本或不确定边界，不能写成普遍结论。

补充内容的目标是让读者“知其然，也知其所以然”，不是把短文扩写成手册。只增加理解问题所必需的原理、步骤、排错和边界。

## 4. Frontmatter 与双层标签

推荐骨架：

```yaml
---
title: "一个具体问题的清晰标题"
summary: "一句话说明问题、关键原因和读者最终能得到什么。"
publishedAt: 2026-01-01
publishedLabel: "2026 年 1 月"
tags: ["具体框架", "协议", "硬件型号", "技术概念"]
listingTags: ["开发方向", "编程语言"]
featured: false
priority: 0
draft: true
readingMinutes: 6
relatedProjects: []
---
```

字段规则：

- `title` 必须指向一个明确问题或使用场景，避免“全面教程”“从入门到精通”等夸张标题。
- `summary` 面向访问者书写，不出现“本文将介绍”“先了解以下内容”等编辑说明。
- `publishedAt` 使用能够确认的日期。只知道月份时用该月第一天作为排序值，并通过 `publishedLabel` 展示真实精度；不要虚构具体发布日期。
- `tags` 用于详情页，可以保留 3–6 个具体标签，例如芯片型号、框架、协议、组件和技术概念。
- `listingTags` 只用于列表卡片和筛选，通常最多两个：一个开发方向，加一个确实出现在文档中的编程语言。
- `readingMinutes` 是可选详情元数据，不会出现在列表卡片；无法合理估算时可以省略。
- `relatedProjects` 只填写仓库内真实存在的学习项目 slug。
- 未完成或仍需核实的文章必须使用 `draft: true`。

### 列表标签推荐词表

开发方向优先从以下词中选择一个：

- `前端`
- `后端`
- `移动端`
- `嵌入式`
- `AI / 算法`
- `数据工程`
- `DevOps`
- `数据库`
- `安全`
- `区块链`
- `系统设计`

编程语言仅在正文确实涉及代码时添加，例如 `C`、`C++`、`Java`、`Python`、`TypeScript`、`ArkTS`、`Cangjie`、`Rust`、`Go` 或 `SQL`。不要把 STM32、MQTT、Spring、BLE、状态机、传感器型号等细标签放进 `listingTags`；这些属于详情页 `tags`。

新增近义分类前先检查现有标签。避免同时出现“服务端”和“后端”、“嵌入式开发”和“嵌入式”等重复分类。

## 5. 正文组织原则

技术笔记不是课程报告，也不是产品宣传页。推荐根据问题选择以下结构，不要求机械地使用所有标题：

1. 问题或使用场景：读者在什么条件下会遇到它。
2. 原因或工作原理：为什么会出现这种现象。
3. 最小可复现步骤：接线、配置、命令或代码。
4. 验证方式：如何判断链路真的工作，而不只是“没有报错”。
5. 快速排错：按最可能、最低成本的顺序检查。
6. 边界与注意事项：版本、性能、安全和适用范围。
7. 参考资料：链接到直接支持关键结论的官方资料。

写作要求：

- 段落短而完整，优先解释因果，不堆砌名词。
- 命令、引脚、错误信息和代码标识使用反引号。
- 表格只用于确实需要逐项映射或对比的内容，列宽由真实内容决定，不添加空列撑版面。
- 删除只服务于编辑者或生成过程的提示语。
- 不为增加篇幅重复用户原文，不写与解决问题无关的技术历史。
- 不虚构性能数据、测试结果、兼容范围或“最佳实践”来源。

## 6. 代码、命令和安全边界

- 示例应尽量短小，保留解释关键机制所需的错误处理、超时和状态边界。
- 伪代码必须明确表现为伪代码，不要伪装成已经运行验证的实现。
- 命令必须标明适用版本或前置状态，避免把连续命令写成无需检查返回值的“固定咒语”。
- 密钥、Token、Wi-Fi 密码、设备鉴权串、私有地址、真实账户、证书和生产配置必须替换为语义明确的占位符。
- 如果源文件含有疑似真实凭据，不得迁入仓库；交付时提醒用户在凭据仍有效的情况下进行轮换。
- 不使用公开前端代码承载任何秘密，也不把本地绝对路径写进正文。

## 7. 图片与图示

- 图片必须帮助理解接线、状态变化、数据流或排错位置；纯装饰图不应插入正文。
- 用户提供的图片先复制到对应的 `public/images/notes/<slug>/`，必要时转换为 WebP，并保留可读细节。
- 图片必须有描述内容和用途的 `alt`；图注补充观察重点，不重复图片标题。
- MDX 中的站内图片路径使用 `withBase()`，确保 GitHub Pages 的 `/BLE/` base 路径正常。
- 不直接发布包含账号、设备标识、密钥、私人信息或无关桌面内容的截图。
- 生成或重绘技术图时，必须保持技术链路正确；不要为了美观改变引脚方向、协议顺序或系统边界。
- 避免超大图片压缩正文宽度。桌面端和移动端都要检查裁切、比例与文件体积。

## 8. 列表、搜索与分页兼容

技术笔记主页由内容元数据驱动：

- 卡片右侧只渲染 `listingTags`，不显示阅读分钟数。
- 左侧筛选项由所有已发布文章的 `listingTags` 自动汇总。
- 搜索可以覆盖标题、摘要、列表标签和详情标签。
- 分页固定为每页 10 篇，由页面脚本自动处理。

因此新增文章通常不需要修改 `src/pages/notes/index.astro`。如果文章没有出现在列表中，依次检查 `draft`、frontmatter 校验、文件扩展名和内容集合，而不是在页面中补硬编码。

## 9. 验证清单

交付前至少完成：

1. 检查 slug、标题、日期、`listingTags` 和 `relatedProjects`。
2. 使用 `rg` 检查占位文字、失效本地路径、账号、密码、Token、Secret、API Key 和设备鉴权信息。
3. 确认引用链接直接支持对应结论，优先使用官方一手资料。
4. 确认新文章能自动出现在列表、搜索和正确的粗粒度筛选下，详情页仍显示细标签。
5. 检查代码块、表格、图片和图注的桌面端与移动端布局。
6. 运行 `npm.cmd run check`。
7. 运行 `npm.cmd run build`。

最终交付说明应列出：新增或修改的文档路径、图片路径、列表分类、关键技术修正、敏感信息处理情况，以及未能执行的验证项。
