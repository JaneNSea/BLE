# Codex 学习项目录入规范

这份文档用于保证 Codex 在不同聊天窗口中新增、迁移或重做学习项目时，仍然遵循同一套内容标准、视觉语言和工程边界。它是 `AGENTS.md` 的学习项目专项补充；两者冲突时，以仓库根目录的 `AGENTS.md` 和用户当次明确要求为准。

## 1. 开始前必须读取的内容

在修改任何学习项目之前，依次读取：

1. 仓库根目录 `AGENTS.md`。
2. 本文档 `docs/CODEX_LEARNING_PROJECT_GUIDE.md`。
3. `src/content.config.ts`，确认当前字段与校验规则。
4. 至少一个结构相近的现有项目，以及 `src/layouts/ProjectLayout.astro`、`src/components/cards/ProjectCard.astro`。
5. 用户提供的报告、README、图片和仓库资料；长文档必须完整读取，不能只根据开头生成摘要。

先用只读检查确认现有改动和目标文件。不要覆盖与本次任务无关的用户修改。

## 2. 内容模型与文件位置

- 学习项目正文放在 `src/content/projects/<slug>.md` 或 `.mdx`。
- slug 使用小写 ASCII kebab-case，例如 `solar-floor-heating-control-system`。
- 普通长文优先使用 Markdown；只有确实需要 Astro/自定义组件时才使用 MDX。
- 项目封面放在 `public/images/projects/<slug>/cover.webp`。
- 不得在首页、项目列表页或卡片组件中硬编码某个项目。发布、排序和首页展示完全由内容集合驱动。
- 新项目默认通过 `npm run new:project -- <slug>` 建立骨架，再按实际资料填写；不得保留模板占位文字。

## 3. 先划清事实边界

整理资料时，把内容分成三类，并在页面中保持区别：

1. **已经实现**：源代码、报告、可运行演示或用户明确说明能够证明的能力。
2. **项目背景与设计目标**：项目为什么值得做、要解决什么问题，可以适度扩写，但不能写成已经实现的结果。
3. **下一阶段方向**：尚未接入的硬件、未来算法、产品化能力或商业计划，必须使用“计划、可扩展、下一阶段”等表述。

不得虚构性能、能耗节省比例、用户量、收入、奖项、课程成绩、发布日期或仓库地址。资料互相冲突时，优先保留可验证的说法，并在正文加入简短的“当前完成边界”。

## 4. Frontmatter 规范

使用当前 schema 支持的字段，不得自行创造页面不会消费的字段。推荐骨架：

```yaml
---
title: "项目名称"
summary: "一句话说明问题、方法与可验证产出。"
cover: "/images/projects/<slug>/cover.webp"
publishedAt: 2026-01-01
updatedAt: 2026-01-01
tags: ["核心技术", "领域"]
featured: false
priority: 0
draft: true
type: "course"
status: "completed"
role: "独立设计与实现"
year: 2026
period: "2026 年"
course: "课程名称"
authors:
  - name: "JaneNSea"
    role: "独立作者"
    avatar: "/avatar.jpg"
repositories:
  - label: "前端仓库"
    stack: "ArkTS · HarmonyOS"
    url: "https://github.com/..."
---
```

字段决策：

- `summary` 面向访客写，不写“本页将介绍”“先了解……”等编辑说明。
- `type` 只能从 `course`、`personal`、`experiment`、`open-source` 中选择。
- `status` 必须反映真实进度；原型可用 `mvp`，已完成的课程成果可用 `completed`，仍在迭代可用 `maintained`。
- `featured: true` 表示进入首页精选；`priority` 越高排序越靠前。修改前先查看现有项目优先级，避免随意挤占主项目。
- 作者必须显式填写。单人项目默认使用 JaneNSea 和 `/avatar.jpg`；多人项目只写用户确认过的公开身份。
- 仓库可以拆成多个 `repositories`。未提供 URL 时不猜测、不搜索相似仓库；保留条目但省略 `url`，或按用户要求暂不展示。
- 日期不明确时不要从项目内容猜测。使用用户确认的时间；若仅能确定网页录入日期，要在交付说明中明确这一点。

## 5. 正文组织原则

学习项目的重点是“怎么学习、怎么判断、怎么解决”，不是把它写成商业产品官网。通常按以下顺序组织：

1. 项目背景与学习目标。
2. 当前完成边界与可验证成果。
3. 系统架构或实现路径。
4. 关键技术难点、决策与取舍。
5. 测试、异常处理和安全边界。
6. 学习过程、复盘与下一阶段方向。
7. 用户提供的完整课程报告或原始技术记录。

迁移用户文档时：

- 尽量保留原始章节、代码、表格、问答和结论，不擅自压缩成长摘要。
- 页面布局已经提供标题，因此删除正文中重复的一级标题。
- 相对源码链接如果在博客仓库中无法访问，应改成可读的代码路径，不保留必然 404 的链接。
- 当前站点未配置 Mermaid 渲染时，将 Mermaid 围栏安全转换为普通代码块；不要让构建失败。
- 删除只服务于编辑者或生成流程的提示语，例如“先阅读以下内容”“这一段用于告诉观者……”。
- Q 与 A 之间保留空行，必要时使用独立段落，确保 Markdown 真正换行。
- 不公开姓名、学号、手机号、密钥、Wi-Fi 凭据、设备令牌、私有仓库地址、生产配置和专有模型参数。

## 6. 封面图规范

没有合适图片时，使用图像生成能力创建独立封面，不复用无关项目素材。

- 画面应先表达项目机制，再追求装饰性；在卡片尺寸下仍能识别核心主题。
- 延续网站的暖色编辑风格：奶油纸张、柔和琥珀、深棕文字语境，以及克制的鼠尾草绿或灰蓝辅助色。
- 避免霓虹、黑色仪表盘、密集电路纹理、廉价环保图标和不可读的小字。
- 不生成品牌 Logo、水印、虚假产品实拍、未经证实的奖章或指标。
- 默认不在图片内放文字，项目名称由网页排版承担。
- 最终 Web 资源优先保存为 WebP，宽度通常控制在 1600px 以内，并检查清晰度与文件体积。
- 保存后用本地图像查看工具检查主体、裁切、文本伪影和技术逻辑。

## 7. 替换或删除旧项目

只有用户明确要求时才能删除现有项目。删除前必须解析并核对正文与素材的绝对路径，确认均位于当前工作区；删除后搜索标题、slug 和素材路径，避免残留死链接。不要为了让首页数量不变而保留假示例。

## 8. 验证清单

交付前至少完成：

1. `rg` 检查旧 slug、失效相对链接、占位文字和敏感信息。
2. 确认新文件能被 `projects` 内容集合自动发现。
3. `npm.cmd run check`。
4. `npm.cmd run build`。
5. 检查首页精选卡片、项目列表和项目详情页的桌面/移动端关键布局。
6. 检查封面路径、作者、目录、仓库信息和正文代码块。

最终交付说明应列出：新增项目路径、封面路径、删除内容、项目完成边界、仓库 URL 是否仍待补充，以及未能执行的验证项。
