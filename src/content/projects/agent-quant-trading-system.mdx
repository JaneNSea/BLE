## App 的运行与开发环境

### 项目概述

本课程设计项目名称为<strong>“Agent量化交易系统”</strong>。项目定位为一个模拟金融行情与模拟交易类移动应用，采用前后端分离与双后端协同架构：前端使用 ArkTS 与 ArkUI 实现鸿蒙移动端页面；Python 后端负责模拟交易 Agent、随机行情生成、技术指标分析、策略决策和 SSE 流式推送；Java 后端负责用户资料、个人中心、搜索、自选股、交易记录等常规业务功能的 CRUD、数据持久化与缓存访问。

项目不接入真实券商交易接口，也不会产生真实买卖行为。系统中的股票行情、虚拟货币行情、K 线数据和交易订单均以课程设计、原型验证和模拟盘演示为目标。这样既降低了真实交易接口和资金安全风险，也便于稳定展示前端状态管理、Java 业务后端、Python Agent 后端、SSE 流式通信和多服务协作流程。

系统主要包含首页、行情页、搜索页、我的页、交易记录页、股票详情页和模拟交易 Agent 页面。首页负责市场概况与资讯展示；行情页负责自选股和市场列表展示；搜索页用于股票检索；我的页用于用户资料、统计与密码修改；交易记录页用于展示模拟交易历史；股票详情页展示单只股票的行情、K 线、基础数据与相关新闻；Trade 页面提供自然语言策略输入，并通过 SSE 接收后端 Agent 的实时分析过程。

## App 需求分析

### 选题过程

选择金融行情与模拟交易方向，主要基于以下考虑：

1.  <strong>移动端场景明确。</strong> 股票、虚拟货币、市场资讯、自选股、交易记录等功能天然适合移动端展示，能够充分体现 App 的界面设计、状态管理与交互能力。

2.  <strong>功能边界清晰。</strong> 一个完整的金融类 App 可以拆分为首页、行情、搜索、详情、个人中心和交易记录等模块，便于按照课程设计要求展示功能结构。

3.  <strong>可扩展性强。</strong> 项目可以从静态数据原型逐步扩展到后端接口、模拟数据、SSE 流式推送和大模型 Agent，具有较好的技术层次。

4.  <strong>适合体现 AI 使用。</strong> 金融分析场景适合引入大模型进行自然语言总结、策略解释和风险提示，同时也适合在开发过程中使用 AI 辅助代码生成、Bug 排查和架构重构。

本项目面向的用户主要是对股票和虚拟货币行情感兴趣、希望快速查看市场信息并尝试模拟交易策略的普通用户。系统希望解决的问题包括：普通用户需要一个清晰现代的行情界面；用户希望查看单只股票的详细信息和 K 线走势；用户希望用自然语言描述策略，并看到系统如何一步步分析；用户需要一个低风险的模拟交易环境，而不是直接接触真实资金交易。

### UI 设计方案与人机交互特性

项目 UI 设计分为两种主要风格。第一种是浅色 iOS/OKX 风格，适用于首页、行情页、搜索页、我的页和交易记录页，主要采用浅色背景、白色卡片、弱分隔线和圆角阴影。第二种是深色交易所风格，适用于股票详情页，通过高对比度文字、红绿涨跌色和紧凑布局提升行情识别效率。

首页包含市场概况、资讯列表和策略入口。市场概况使用横向滑动列表展示指数卡片，资讯使用纵向列表展示。行情页主要包括自选股和市场列表，开发时重点处理了异步加载后的 UI 刷新问题。股票详情页围绕单只股票展示，包含顶部导航、行情概览、周期切换、K 线图、操作按钮、基础数据和相关新闻。Trade 页面采用类似 ChatGPT 的对话式界面，不再使用传统表单堆叠方式，用户输入策略后，系统将用户消息加入消息流，然后后端持续推送 Agent 的执行过程。

>
> 本项目并非简单堆叠页面，而是围绕“行情阅读效率”和“Agent 执行过程可见性”进行设计。普通行情页强调稳定、简洁、清晰；股票详情页强调专业感和信息密度；Trade 页面强调对话式交互和流式反馈。

## App 架构设计及技术实现方案

### 总体架构

本项目采用前后端分离与双后端协同架构，前端负责页面展示、用户输入、状态管理与 SSE 流式解析；Java 后端负责常规业务接口、数据库持久化、缓存访问和 CRUD 逻辑；Python 后端负责模拟交易 Agent、行情生成、技术指标计算、策略决策、模拟订单生成和大模型总结。这样的划分使常规业务与 AI/流式任务解耦，避免把所有逻辑堆在一个后端服务中。

### 前端核心技术实现

#### 统一请求封装

为了避免每个页面重复写 HTTP 请求逻辑，项目将请求封装为统一的 `request<T>` 方法。封装内容包括基础地址、请求方法、请求头、超时时间、参数序列化和 JSON 解析。

```
export async function request<T>(
  url: string,
  method: http.RequestMethod,
  data?: object
): Promise<BaseResponse<T>> {
  const httpRequest = http.createHttp()
  const options: http.HttpRequestOptions = {
    method,
    header: { 'Content-Type': 'application/json' },
    extraData: data ? JSON.stringify(data) : '',
    readTimeout: 10000,
    connectTimeout: 10000
  }
  const response = await httpRequest.request(`${BASE_URL}${url}`, options)
  return JSON.parse(response.result as string)
}
```

该封装的作用是统一前后端数据对接方式，并减少页面层代码复杂度。实际开发中还可以继续加入 Token、错误码统一处理、重试策略和日志打印。

#### 首页并发加载

首页需要同时加载市场概况、资讯列表和策略列表。如果串行请求，会增加等待时间。因此使用 `Promise.all` 并行请求多个接口，全部返回后再统一更新状态。需要注意的是，`Promise.all` 中任意一个接口失败都会进入 `catch`，如果希望部分接口失败不影响其他区域展示，可以为每个请求单独包裹 `try-catch` 或使用 `Promise.allSettled`。

#### 涨跌颜色判断

金融行情类 App 中，涨跌颜色是非常关键的视觉表达。本项目通过解析字符串形式的涨跌幅，例如 `+0.85%` 和 `-1.23%`，转换为数字后判断颜色。

```
getChangeColor(changePercent: string): ResourceColor {
  const num = parseFloat(changePercent.replace('%', ''))
  if (num > 0) return '#FF3B30'
  if (num < 0) return '#34C759'
  return '#8E8E93'
}
```

#### SSE 流式接收

Trade 页面不能使用普通 `request()` 等待完整响应，因为 Agent 返回的是持续事件流。前端需要使用 `requestInStream()` 接收二进制 chunk，并通过缓冲区解析完整 SSE 事件。

> <strong>前端 SSE chunk 解析流程</strong>
>
> 收到 chunk → 转为字符串 → 追加到 streamBuffer → 按 `\n\n` 切分完整事件块 → 解析 event/data → 渲染消息或更新页面状态。

核心思想是：SSE 数据可能被网络层拆成不完整片段，不能假设每次回调都刚好是一条完整消息。必须维护 `streamBuffer`，只有遇到 `\n\n` 才认为一个事件块结束。

### Java 业务后端设计

Java 后端主要承担稳定、结构化、可持久化的业务能力，适合处理用户资料、个人中心、搜索、自选股、交易记录等传统后台功能。与 Python Agent 后端相比，Java 后端更强调接口稳定性、分层清晰和数据库事务一致性。

| <strong>层次</strong> | <strong>职责说明</strong> |
|:---|:---|
| Controller 层 | 接收前端 REST 请求，完成参数校验、路由分发和统一响应包装。 |
| Service 层 | 编写核心业务逻辑，例如用户资料修改、交易记录查询、搜索结果整理和自选股管理。 |
| Repository 层 | 负责与 MySQL 交互，完成实体查询、插入、更新和删除。 |
| 实体与 DTO/VO 层 | 将数据库实体、前端请求体和前端响应体分开，避免直接暴露数据库结构。 |
| 缓存与配置层 | 使用 Redis 做部分状态缓存或热点数据缓存，使用配置文件管理数据库、端口和跨域等参数。 |

Java 后端与 Python 后端的关系不是互相替代，而是分工互补：Java 负责稳定业务底座，Python 负责更灵活的 Agent 推理和流式任务。前端根据接口类型分别调用对应服务，普通页面优先访问 Java 后端，Trade 页面访问 Python Agent 后端。

### 后端 Agent 设计

> <strong>模拟交易 Agent 执行流程</strong>
>
> 读取用户策略 prompt 与交易配置  
> ↓  
> 生成指定 symbol 的模拟行情 OHLCV  
> ↓  
> 计算 MA5 / MA20 / MA60 / RSI14 / 成交量比等指标  
> ↓  
> 基于规则生成 BUY / SELL / WATCH 决策  
> ↓  
> 生成模拟订单或观察结果  
> ↓  
> 调用大模型生成自然语言总结，失败则使用规则摘要 fallback  
> ↓  
> 通过 SSE yield 推送本轮事件  
> ↓  
> 等待 intervalSeconds 后进入下一轮，直到停止。

```
@app.post("/api/trade/start")
async def start_trading_task(req: StartTaskRequest):
    session_id = str(uuid.uuid4())
    return StreamingResponse(
        autonomous_trading_loop(session_id, req.prompt),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Session-Id": session_id
        }
    )
```

### 算法与策略说明

本项目没有使用复杂机器学习算法，而是使用规则策略和常见技术指标进行模拟交易分析。主要指标包括 MA5/MA20/MA60、RSI14、成交量比、周期涨跌幅和价格区间位置。策略决策逻辑大致如下：若 MA5 高于 MA20、周期涨幅为正、量能放大且 RSI 未明显过热，则倾向于 `BUY`；若 MA5 低于 MA20 且周期涨幅为负，则倾向于 `SELL`；其他情况倾向于 `WATCH`；同时根据波动幅度、成交量放大程度和 RSI 状态给出风险等级。

## 技术亮点、技术难点及解决方案

### 技术亮点

#### Java + Python 双后端分工明确

本项目没有把所有后端逻辑都堆在一个服务中，而是采用了 Java 业务后端与 Python Agent 后端并行的设计。Java 后端主要负责用户资料、个人中心、搜索、自选股、交易记录等常规业务接口，适合处理结构化 CRUD、数据库事务、缓存访问和稳定业务逻辑；Python 后端主要负责模拟交易 Agent、随机行情生成、技术指标分析、策略决策、大模型总结和 SSE 流式推送，适合处理 AI 调用、异步任务和实时推流。

这种设计的好处是服务边界比较清晰。普通业务接口保持稳定，Agent 相关逻辑保持灵活，两者不会互相污染。对前端而言，普通页面主要访问 Java 后端，Trade 页面主要访问 Python Agent 后端；对后端而言，Java 和 Python 各自发挥适合自己的优势。

#### SSE 流式推送实现 Agent 执行过程可视化

Trade 页面不是普通的“一次请求、一次返回”页面，而是一个持续接收 Agent 执行过程的流式界面。用户输入自然语言策略后，后端会持续推送 open、agent_stepanalysissummary等事件，前端再把这些事件渲染成类似聊天记录的消息流。

这个设计比普通 HTTP 请求更适合模拟交易 Agent 场景。因为 Agent 的执行过程包含行情生成、指标计算、策略判断、大模型总结等多个步骤，如果等全部执行完再返回，用户无法知道当前系统是否仍在工作。SSE 可以让用户实时看到后端正在做什么，增强了交互透明度和系统可信度。

#### 前端 requestInStream 与 streamBuffer 解决 SSE 分片问题

在前端实现 SSE 接收时，不能简单地认为每次收到的数据块都是完整事件。网络传输中 SSE 数据可能被拆成多个 chunk，如果直接解析，容易出现 JSON 不完整、事件缺失或页面无响应的问题。

本项目在前端维护了 `streamBuffer` 缓冲区。每次收到二进制数据后，先转成字符串并追加到 buffer 中，再根据 `\n\n` 切分完整事件块。只有完整事件块才会进入 event 和 data 解析流程。这个设计解决了流式响应中的半包问题，使前端能够稳定接收后端 Agent 的连续输出。

#### Canvas 绘制股票详情页 K 线图

StockDetail 页面没有停留在简单文本展示，而是通过 Canvas 绘制 K 线图。K 线图包含价格网格线、蜡烛实体、上下影线、成交量柱、最新价横线和价格标签。绘制过程中需要根据最高价和最低价计算价格区间，再将价格映射到 Canvas 的 Y 坐标，同时根据开盘价和收盘价决定上涨或下跌颜色。

这一部分体现了移动端图形绘制和数据可视化能力。相比只展示列表和文字，K 线图让股票详情页更接近真实金融交易类 App，也提升了课程设计的完整度和展示效果。

#### 加载态、空态、错误态和停止态较完整

项目不是只考虑接口成功时的页面展示，也考虑了加载失败、数据为空、Agent 运行中、Agent 停止、大模型不可用等状态。比如 Trade 页面在 Agent 运行时切换按钮状态，heartbeat 不作为普通消息刷屏，而是更新底部状态；搜索页和交易记录页增加加载态、空态和错误提示；Python Agent 在大模型不可用时使用 fallback 摘要保证流程继续。

这些细节虽然不是最复杂的算法，但非常接近真实 App 开发中的工程要求。一个 App 是否可靠，往往取决于异常状态是否处理完整，而不是只看正常路径是否能跑通。

### 技术难点与解决方案

#### 难点一：普通 HTTP 请求无法处理 SSE 流式响应

Trade 页面最开始如果使用普通 `request()` 请求，会等待后端完整返回。但 Agent 后端返回的是 `text/event-stream`，连接会持续保持，普通请求封装很难拿到中间过程，表现为前端和后端都像“没有后续反应”。

> <strong>解决方案</strong>
>
> 将 Trade 页面与普通 REST 页面区分开。普通页面继续使用统一 `request<T>` 封装；Trade 页面使用 `requestInStream()` 接收流式数据。在 `dataReceive` 回调中持续读取 chunk，并用 `streamBuffer` 解析完整 SSE 事件。这样既保留了普通接口封装的简洁性，也满足了 Agent 流式推送的特殊要求。

#### 难点二：SSE chunk 分片导致事件解析不完整

SSE 数据在网络传输中可能被拆分。一个完整事件可能分两次甚至多次返回，也可能一次返回多个事件。如果前端每收到一个 chunk 就直接解析 JSON，很容易出现解析失败、消息丢失或界面卡住。

> <strong>解决方案</strong>
>
> 前端维护一个字符串缓冲区 `streamBuffer`。每次收到新 chunk 后先追加到缓冲区，再按 `\n\n` 切分完整事件块。最后保留尚未完整的尾部数据，等待下一次 chunk 到来后继续拼接。这样可以同时处理半包和粘包问题。

#### 难点三：Agent 长连接任务如何停止

模拟交易 Agent 启动后会持续循环分析行情。如果只建立 SSE 连接而不设计任务状态管理，用户点击停止时，后端可能并不知道应该停止哪一个任务，导致任务继续运行、前端状态错乱或资源无法释放。

> <strong>解决方案</strong>
>
> Python 后端为每个 Agent 任务生成唯一 `session_id`，并使用 `active_tasks` 字典保存运行状态。  
> 启动任务时将对应 session 标记为运行中，停止接口收到 session 后将其置为停止。  
> Agent 主循环中定期检查该状态，一旦发现停止信号就退出循环，并推送 `done` 事件给前端。

#### 难点四：ArkUI 中 `@Builder` 参数传递导致 UI 不刷新

行情页开发中，“自选”列表在异步数据加载完成后仍然显示空状态，而其他列表可以正常渲染。排查后发现问题与 ArkUI 中 `@Builder` 自定义构建函数的参数传递机制有关。初始阶段 `@Builder` 接收到空数组，后续异步请求更新状态变量后，Builder 内部没有正确感知外部状态变化。

> <strong>解决方案</strong>
>
> 将数组直接传参改为对象包裹传参，并配合 \$\$ 语法实现按引用绑定。这样 Builder 内部能够感知外部状态变化，异步请求完成后页面可以正确重新渲染。同时对项目中其他使用 `@Builder` 的位置进行检查，避免类似问题再次出现。

#### 难点五：前后端返回结构理解错误

首页开发中曾经出现过“后端有数据，但前端列表为空”的问题。原因是前端误以为 `data` 字段直接是数组，实际后端返回的是一个对象，数组位于 `data.indexSummary` 里面。泛型写错后，即使接口请求成功，页面也无法正确取值。（属于是利用ai开发时候，如果切换用不同ai做开发或者上下文长度超限了都有可能发生的事情。

> <strong>解决方案</strong>
>
> 对接接口前先查看后端 Swagger、实体类或实际返回 JSON，确认包装层、字段名和数组位置。前端泛型要和后端 VO/DTO 对齐，不能凭感觉写。尤其是 `BaseResponse<T>` 这类统一响应结构，要明确 `data` 内部到底是对象还是数组。

#### 难点六：Scroll + Column 布局导致页面顶部留白

在“我的页”和部分列表页面中，曾经出现内容看起来被垂直居中、顶部空白过大的问题。这个问题不是单个组件内容写错，而是 `Scroll`、`Column`、安全区和导航栏占位共同影响导致的布局问题。

> <strong>解决方案</strong>
>
> 避免内部 `Column` 强制撑满高度，保持内容自适应；外层 `Scroll` 和内部 `Column` 同时设置顶部对齐；结合安全区处理，避免系统状态栏造成视觉留白。如果外层使用 `Navigation` 或 `NavDestination`，还需要检查标题栏是否存在额外占位。

#### 难点七：Java 后端登录认证不能只做简单账号密码查询

登录功能表面上只是提交账号和密码，但后端实现时不能只做一次数据库查询后直接返回结果。本项目的登录后端使用 Java Spring Boot 实现，并引入 JWT 与 BCrypt。这里的难点主要有两个：第一，密码不能明文比对和明文存储，需要使用 BCrypt 做安全校验；第二，登录成功后不能只返回用户信息，还需要生成后续接口可识别的 JWT，让前端后续请求能够维持登录状态。

在实际实现中，后端需要在登录接口中完成账号查询、BCrypt 密码比对、JWT 生成和统一响应返回。如果账号不存在、密码错误或者用户信息异常，都不能继续签发 Token。否则前端虽然能跳转页面，但后续接口无法判断用户身份，系统也缺少基本安全边界。

> <strong>解决方案</strong>
>
> 后端使用 Java Spring Boot + JWT + BCrypt 进行登录认证。登录时先根据用户名查询用户，再使用 BCrypt 校验用户输入密码与数据库中保存的加密密码是否匹配。校验成功后，通过 `JwtUtil.generateToken(Long userId, String username)` 生成 JWT，其中 `subject` 保存用户 ID，`claim("username", username)` 保存用户名，并设置签发时间和过期时间。JWT 密钥从 `qta.jwt.secret` 配置读取，过期时间通过 `qta.jwt.expiration-seconds` 配置，默认 86400 秒。

<strong>后端设计亮点：</strong>登录认证没有直接返回数据库用户对象，而是使用 JWT 作为后续接口的身份凭证；密码校验使用 BCrypt，避免明文密码风险；JWT 的密钥和过期时间通过配置项管理，而不是写死在代码中。这样 Java 后端既能承担稳定业务接口，也能作为整个系统的身份认证中心。

#### 难点八：前端登录状态需要同时解决当前会话和应用重启后的保留问题

前端登录功能的难点不是只把 Token 放到一个变量里。移动端应用存在页面切换、应用进入后台、应用重启等情况。如果只使用内存变量保存 Token，应用重启后登录状态会丢失；如果每次请求都直接读本地持久化存储，又会增加不必要的读取成本，也不利于统一状态管理。

本项目登录页采用了 Token 双存储方案：登录成功后，先把 Token 写入 `AppStorage`，用于当前运行会话中的快速读取；再把 Token 写入 `Preferences`，用于应用关闭或重启后恢复登录状态。这样既保证了当前会话访问效率，也解决了重启后自动登录的问题。

> <strong>解决方案</strong>
>
> 前端登录成功后，判断后端响应满足 `res.code === 0` 且 `res.data?.token` 存在。
>
> 随后执行两步 Token 存储逻辑：
>
> 第一步，使用 `AppStorage.setOrCreate(’auth_token’, res.data.token)` 保存当前会话 Token；
>
> 第二步，通过 `preferences.getPreferencesSync(getContext(), { name: ’auth’ })` 获取本地持久化对象， 并依次执行 `pref.putSync(’token’, res.data.token)` 写入本地 Token、`pref.flush()` 持久化落地。
>
> 存储完成后，通过 `router.replaceUrl({ url: ’pages/Index’ })` 跳转到首页。

<strong>前端设计亮点：</strong>前端没有把登录状态只放在页面变量中，而是形成了“内存 + 持久化”的双层状态管理。当前会话中使用 `AppStorage` 读取更方便，应用重启后可以从 `Preferences` 恢复，兼顾了性能和用户体验。登录成功后使用 `replaceUrl` 而不是普通跳转，也能减少用户返回登录页造成的交互问题。

#### 难点九：入口页需要恢复 Token，否则应用重启后无法自动登录

即使登录页已经把 Token 存入 `Preferences`，如果入口页不做恢复逻辑，应用重启后内存中的 `AppStorage` 仍然是空的。这样请求封装读取不到 Token，页面也会误判为未登录。这个问题容易被忽略，因为开发调试时应用经常保持在同一运行会话中，看起来登录状态正常，但一旦关闭应用或重新启动，就会暴露问题。

因此，入口页必须在页面出现时主动检查登录状态。检查顺序不能直接只读本地持久化，而应该先读 `AppStorage`，如果内存中没有，再读 `Preferences`。如果从持久化中读到了 Token，还需要重新写回 `AppStorage`，这样后续请求封装可以继续从统一位置读取 Token。

> <strong>解决方案</strong>
>
> 在入口页的 `aboutToAppear()` 生命周期中恢复登录状态。首先调用 `AppStorage.get<string>(’auth_token’)` 读取内存 Token； 如果内存 Token 为空，再通过 `preferences.getPreferencesSync(getContext(), { name: ’auth’ })` 读取本地保存的 `token`。 如果本地存在有效 Token，则调用 `AppStorage.setOrCreate(’auth_token’, token)` 将 Token 恢复至内存， 并通过 `this.isLoggedIn = !!token` 更新页面全局登录状态，实现应用打开自动登录。

<strong>前端设计亮点：</strong>入口页承担了登录态恢复职责，使登录状态不只依赖登录页本身。这个设计把“是否已登录”的判断前置到应用入口，避免每个页面都重复读取 `Preferences`。同时，恢复后重新写入 `AppStorage`，让后续页面和请求封装都能从同一个内存键中获取 Token，状态流更加清晰。

#### 难点十：请求封装必须自动携带 JWT，否则登录状态无法贯穿业务接口

登录成功并保存 Token 只是第一步。如果后续请求没有自动携带 Token，Java 后端仍然无法识别当前用户，用户资料、个人中心、交易记录、自选股等接口就无法和登录用户绑定。手动在每个接口里添加 Token 也不合理，因为容易遗漏，代码重复，并且后续修改认证格式时维护成本很高。

> <strong>解决方案</strong>
>
> 本项目在统一请求封装中全局处理 Token 携带逻辑，业务页面无需单独适配。 每次发送网络请求前，框架自动从 `AppStorage` 中读取全局存储的 `auth_token`； 若 Token 存在，则自动在请求头中拼接 `Authorization: Bearer xxx` 身份认证参数。
>
> 核心封装逻辑位于前端 `request<T>` 工具方法中，默认统一配置 `Content-Type: application/json` 请求头， 再获取内存 Token 完成身份头拼接，即 `header[’Authorization’] = ’Bearer ’ + token`。 所有业务接口请求均可直接调用统一 `request<T>` 方法，自动携带 JWT 令牌， Java 后端可通过解析请求头中的 Authorization 参数识别、校验用户身份。

### AI 在本项目中的使用方式

本项目确实大量使用了 AI 辅助开发，但并不是采用完全黑盒式的 Agent workflow 直接生成整个项目。我的实际做法更接近“人为主导架构，AI 辅助分块实现”：先由我确定项目主题、技术边界、页面结构、前后端职责和开发顺序，再让 AI 针对某一个具体模块生成代码、解释报错或提供优化思路。

本项目中 AI 主要参与了以下几类工作：

1.  <strong>选题与灵感收集：</strong> 在最开始阶段，我通过和 AI 对话，筛选金融行情、量化交易、Agent 分析等方向，最终确定“Agent 量化交易系统”这一选题。

2.  <strong>技术方案讨论：</strong> AI 辅助比较了 Java 后端、Python 后端、RUST后端等技术方案，但最终技术取舍由我根据课程要求和项目可实现性判断。

3.  <strong>小 Demo 验证：</strong> 在正式开发前，先让 AI 辅助生成一些局部 Demo，例如 ArkTS 页面跳转、登录 Token 存储、HTTP 请求封装、SSE 流式解析、Canvas 绘制 K 线等，用来确认关键功能确实能做出来。

4.  <strong>前端页面开发：</strong> AI 辅助生成了首页、行情页、搜索页、股票详情页、Trade 页面、我的页、交易记录页等页面的基础结构，我再根据实际运行结果进行调整。

5.  <strong>Java 后端开发：</strong> AI 辅助生成用户登录、JWT 工具类、用户资料、搜索、自选股、交易记录等常规业务接口的部分代码，但接口字段、数据库结构和返回格式需要人工确认。

6.  <strong>Python Agent 后端开发：</strong> AI 辅助设计了 FastAPI 接口、模拟行情生成、技术指标计算、策略决策、大模型总结和 SSE 推流逻辑。

8.  <strong>文档整理：</strong> AI 辅助将开发过程中的技术点、难点和经验整理成课程设计报告，主要是借助AI进行格式上的调整利用AI去做latex文档便于排版的美观，将自己的观点想法思路输入进去由AI进行整理最终可以得到文档。

### AI 使用边界

通过本项目，我对 AI 辅助开发的边界有了更明确的认识。AI 可以极大提高开发效率，但不能代替开发者做最终判断。尤其是本项目涉及登录认证、Token 存储、Java 后端接口、Python Agent 服务和数据库结构，不能完全依赖 AI 的默认方案。

本项目中，我对 AI 生成代码设置了以下边界：

1.  不允许 AI 擅自改变整体目录结构；

2.  不允许 AI 擅自引入新的数据库、中间件或复杂框架；（这很重要，最开始我做过一版让AI告诉我架构思路，但是我发现复杂度远超出我的想象）

3.  不允许 AI 为了通过编译而删除核心业务逻辑；

4.  不允许 AI 将普通 REST 请求和 SSE 流式请求混在同一个封装中；

5.  不允许 AI 把登录 Token 随意存在页面变量中；

6.  不允许 AI 一次性重构多个页面或多个后端模块；（这也很重要，防止突然出现bug不好重新调整）

7.  当然还有很多边界需要去做，未来开发的时候可以去网上找一份软件开发规范的skill给AI，或者自己写一份开发规范。

> <strong>我的理解</strong>
>
> AI 更适合作为“局部实现助手、Debug 辅助工具、方案讨论对象和文档整理工具”，不适合作为完全自由发挥的项目架构师。真正可靠的开发方式，是由人控制项目边界和开发节奏，让 AI 在明确边界内提高效率。

## AI 代码开发 SOP

### SOP 总览

结合本项目开发过程，我总结出一套更适合课程设计和中小型项目的 AI 辅助开发 SOP。它不是让 AI 从零自动生成全部代码，而是让 AI 参与每一个可验证可调整可改动的小步骤。

> <strong>AI 辅助开发 SOP</strong>
>
> 灵感收集 → 技术验证 → 可行性 Demo  
> → 功能树与页面草图 → 搭建项目骨架与导航  
> → 后端接口先行，前端按接口接入 → 核心功能优先完成  
> → 外围功能补齐与 UI 美化 → 测试、回滚、文档整理

### 第一步：灵感收集

项目开始时，不应该直接问 AI“帮我写一个 App”，而应该先确定现实需求和项目价值。可以先从自己的生活体验、常用 App、应用商店、GitHub 项目、课程要求和 AI 对话中收集灵感。

### 第二步：技术验证

AI 很容易给出看起来很完整但实际过于复杂的技术方案。例如一开始可能会建议使用更多数据库、中间件或复杂架构，但课程项目并不一定需要这些东西。因此技术验证阶段不能完全相信 AI，而要判断每个技术是否真的必要。

本项目最终采用：

- 前端：ArkTS + ArkUI；

- Java 后端：Spring Boot + JWT + BCrypt + MySQL + Redis；

- Python 后端：FastAPI + SSE +langChain；

- 通信方式：普通业务用 REST，Agent 流式输出用 SSE。

这个选择不是为了堆技术，而是因为 Java 更适合稳定 CRUD 和登录认证，Python 更适合 Agent、行情模拟和大模型调用，ArkTS 则是鸿蒙 App 开发的主要语言。

### 第三步：可行性 Demo

正式开发前，必须先写小 Demo 验证关键技术，而不是一开始就搭完整项目。这样做的好处是可以提前发现技术坑，避免后期大面积返工。

本项目中较关键的 Demo 包括：

1.  Token 存储 Demo：验证 `AppStorage` 和 `Preferences` 是否能保存和恢复登录状态；

2.  HTTP 请求 Demo：验证前端能否正常调用 Java 后端接口；

3.  SSE 流式 Demo：验证前端能否通过 `requestInStream()` 接收 Python 后端事件流；

4.  Canvas 绘图 Demo：验证股票详情页 K 线图能否绘制；

5.  Java 登录 Demo：验证 BCrypt 校验和 JWT 生成是否可用；

6.  Python Agent Demo：验证模拟行情、技术指标和策略决策是否能串起来。

### 第四步：功能树与页面草图

当 Demo 验证通过后，才进入正式项目开发。正式开发前，需要先画出功能树和页面结构，而不是直接写代码。

本项目的功能树大致包括：

- 登录与认证模块；

- 首页市场概况模块；

- 行情与自选股模块；

- 搜索模块；

- 股票详情模块；

- Trade Agent 模块；

- 我的页与用户资料模块；

- 交易记录模块。

页面草图阶段主要解决四个问题：

1.  App 有几个主要页面；

2.  每个页面放哪些内容；

3.  页面之间如何跳转；

4.  哪些状态由当前页面持有，哪些状态需要全局共享。

### 第五步：先搭页面骨架与导航

前端开发不能一开始就追求界面细节。更稳的方式是先搭页面骨架，用简单文字占位确认跳转链路。比如先用 `Text("首页")`、`Text("行情页")`、`Text("Trade 页面")` 占位，确认路由正常后，再逐步填充内容。

本项目中，登录页、首页、行情页、搜索页、股票详情页、Trade 页面、我的页和交易记录页都需要相互配合。如果导航方式混乱，后期改动会非常麻烦。因此前期先确认页面入口、跳转方式和登录后的默认页面，是非常必要的。

### 第六步：后端接口先行，前端按接口接入

每开发一个页面，不能前端凭感觉写字段。更合理的顺序是：

> <strong>页面与接口开发顺序</strong>
>
> 确认页面需要展示的数据字段 → 设计数据库表和 Entity → 编写 DTO / VO → 编写 Service 和 Controller  
> → 使用 Apifox 等工具测试接口 → 把接口路径、请求方式、请求体和返回 JSON 交给前端 → 前端根据真实字段接入页面

本项目中，Java 后端接口开发基本遵循这个顺序。这样可以减少前端字段猜错、对象数组判断错误、返回结构不一致等问题。

### 第七步：核心功能优先

项目开发过程中，必须区分核心功能和外围功能。核心功能如果做不出来，项目就缺少竞争力；外围功能做得再多，也只能算页面堆叠。

本项目的核心功能包括：

- 登录认证与 Token 自动携带；

- Trade 页面自然语言策略输入；

- Python Agent 模拟行情生成；

- 技术指标计算与策略决策；

- SSE 流式推送与前端消息展示；

- 股票详情页 K 线可视化。

UI 美化、资讯列表、空态优化、交易记录细节等属于外围增强功能，应当在核心功能跑通后再逐步补齐。

### 第八步：每次 AI 生成后都要测试和回滚准备

AI 生成代码速度很快，但也容易把项目改乱。因此每次让 AI 修改前，都应该明确它要改哪些文件、为什么改、影响哪些功能。修改后要立即测试，确认能编译、能运行、接口能通。

如果使用 Git，建议每完成一个稳定功能就提交一次；如果不熟悉 Git，也应该定期压缩备份项目。这样即使 AI 把代码改乱，也可以回到上一个可运行版本。

## 现代化软件开发思考

### 从“写完功能”到“稳定迭代”

通过本项目，我对开发规范的理解发生了变化。好的开发规范不是代码看起来漂亮，而是当需求变多、页面变多、后端服务变多、AI 参与变多以后，项目仍然可以稳定迭代。

本项目如果没有规范，很容易出现以下问题：

- 前端页面各写各的请求逻辑；

- Java 后端和 Python 后端接口归属混乱；

- 登录 Token 在多个页面重复保存；

- 同一个 UI 卡片被 AI 生成多套版本；

- SSE 流式请求被当作普通 JSON 请求处理；

- 数据库 Entity、DTO、VO 混用；

- Bug 修复后没有记录，后续又重复踩坑。

因此，现代化软件开发的重点不是堆复杂架构，而是保证边界清楚、变更可控、接口稳定、状态可追踪、问题可定位。

### 状态管理是移动端开发的核心

在移动端开发中，状态管理比单纯写 UI 更重要。比如登录状态、加载状态、错误状态、空状态、列表数据状态、Agent 运行状态，都必须有明确归属。

本项目中比较典型的状态包括：

- 登录 Token：当前会话放在 `AppStorage`，持久化放在 `Preferences`；

- 页面加载状态：由对应页面管理；

- SSE 连接状态：由 Trade 页面管理；

- Agent 运行状态：前端用 `running` 标记，后端用 `active_tasks` 标记；

- 列表数据状态：包括加载中、加载成功、为空、加载失败。

状态归属清楚以后，页面刷新、登录恢复、按钮禁用、错误提示和任务停止才会稳定。

### 重用比重复更重要

AI 参与开发后，很容易出现“同一个功能多种实现”的问题。比如请求封装、卡片组件、错误提示、空态页面、Token 读取逻辑，如果每个页面都让 AI 单独写一套，短期能跑，长期会很难维护。

因此，本项目更适合采用组件化和工具化思路：

- 公共 HTTP 请求放在 `network` 层；

- SSE 解析逻辑单独封装；

- 涨跌颜色、日期格式化等放在 `utils`；

- 市场卡片、新闻卡片、消息气泡等抽成组件；

- Java 后端统一返回格式；

- Java 后端区分 Entity、DTO、VO；

- Python Agent 保持独立模块，不和普通业务接口混写。

真正能长期维护的项目，不是每个功能都重新写一遍，而是不断沉淀可复用构件。

### 先功能，再健壮，最后美观

本项目开发过程中，我也认识到开发顺序不能反过来。最开始应该先让核心功能跑通，例如登录、接口请求、Agent 推流、K 线展示；然后再处理健壮性，例如异常提示、空态、停止任务、Token 恢复；最后再做美观，例如卡片阴影、间距、配色、动画等。

## 学习感悟及对课程的建议

### 关于 App 开发流程的感悟

通过本次课程设计，我对 App 开发流程有了更完整的认识。App 开发不是直接打开 IDE 写代码，而是应该经历选题、构思、功能拆分、Demo 验证、页面草图、项目骨架、逐个功能实现、组合构建、测试打磨和最终发布等步骤。

过去我容易把开发理解为“把页面和接口写出来”，但这次项目让我意识到，真正重要的是开发顺序和边界控制。比如，如果没有先验证 SSE Demo，后面 Trade 页面就会卡在流式接收上；如果没有先做登录状态恢复，后面我的页和交易记录页就无法稳定判断用户身份；如果没有先确认接口字段，前端就会在错误数据结构上浪费很多时间。

### 关于 AI 辅助开发的感悟

AI 对本项目帮助很大，但也暴露出很多问题。AI 能快速生成代码，也能快速给出方案，但它不一定了解项目真实边界。如果提示词不够明确，AI 可能会重复造轮子、引入不必要技术、混用不同风格，甚至为了修一个报错改坏其他模块。

我认为使用 AI 开发时，最关键的是：

1.  先由人做架构设计和模块切分；

2.  每次只让 AI 处理一个小任务；

3.  AI 生成代码后必须人工阅读；

4.  关键功能必须自己理解；

5.  所有接口必须实际测试；

6.  所有稳定版本必须保存或提交；

7.  不要让 AI 完全主导项目结构。

这次项目让我认识到，AI 不是替代学习的工具，而是放大学习效率的工具。前提是开发者自己必须知道项目要往哪里走。

### 关于前后端联调的感悟

本项目的前后端并不是一个简单后端，而是 Java 和 Python 两套服务。Java 后端负责普通业务，Python 后端负责 Agent 流式任务。前端同时对接两种接口后，我明显感受到接口契约的重要性。

后端接口写完后，一定要先用 Apifox、Postman 或 curl 测试，再交给前端。前端接入前也必须确认：

- 请求地址是否正确；

- 请求方法是 GET、POST 还是 PUT；

- 请求体字段是否完整；

- 返回的 `data` 是对象还是数组；

- 是否需要携带 Token；

- 是否是普通 JSON 响应还是 SSE 流式响应。

只要这些细节不确认，前端就会出现“页面没反应”“列表为空”“接口 422”“Token 无效”等问题。

### 关于课程学习的收获

本课程设计让我真正经历了一个 App 从选题到开发、从 Demo 到集成、从能跑到可展示的过程。相比单独学习某个语法点，完整项目更能暴露真实问题。例如 UI 状态刷新、页面导航、接口字段、登录保持、流式通信、数据库结构、后端分层、测试和打包，这些问题只有在完整项目中才会集中出现。

我最大的收获是：开发能力不是只看会不会写某段代码，而是看能不能把一堆功能组织成一个可以运行、可以解释、可以维护的系统。

## 后续优化方向

本项目目前已经形成了一个可展示的 MVP，但如果继续完善，可以从以下方向优化。

### 完善 Java 后端业务能力

Java 后端可以继续完善用户体系、自选股管理、交易记录查询、权限校验和统一异常处理。后续可以增加接口分页、条件查询、统一错误码、操作日志和更完整的 Token 过期处理。

### 完善 Python Agent 能力

Python Agent 当前主要使用模拟行情和规则策略。后续可以增加更真实的策略解析能力，让大模型把自然语言策略转换成结构化条件，例如指标条件、止损比例、止盈比例、仓位比例和执行周期。

### 增加策略回测

当前系统偏实时模拟展示，后续可以加入回测模块。系统可以保存历史行情和每次策略决策结果，计算收益率、最大回撤、胜率、盈亏比和夏普比率等指标。这样 Agent 的建议不只是展示文本，而是可以用数据评估。

### 增强 K 线图和行情可视化

StockDetail 页面后续可以支持分时图、MA、MACD、RSI、BOLL 等指标切换，也可以支持横屏查看、缩放、滑动和十字光标。这样股票详情页会更接近真实交易类 App。

### 增强系统健壮性

后续可以继续完善断网处理、后端服务未启动提示、SSE 中断重连、Token 过期跳转登录、接口超时重试等功能。尤其是 Trade 页面，由于是长连接流式任务，更需要处理网络异常和任务状态恢复。

## Q&A 自己的一些思考

### 问题 1

<strong>Q：现在agent的workflow能完成全栈开发吗？</strong>

<strong>A：workflow的工作模式有点像黑盒，尽管说现在主流的几个产品会添加运行测试纠正，但是依旧不能保证产品输出的稳定性及可用性扩展性，而且由agent直接产出的产品，你要花大量的时间去把复杂的逻辑给梳理清楚，才有办法去做改动，现在主流的workflow框架应该是产品经理，前端后端等人员架构模式，这样的架构模式其实已经是企业的传统架构模式了，现在主流的企业项目结构应该是面向项目的，以项目为中心，而且ai在各方面的能力其实都是很强的，传统的架构模式是因为个人能力职能有限，并且在很多情况下，边缘所带来的创造力是无限的，ai很多在边缘的产出都是非常有想象力的。</strong>

### 问题 2

<strong>Q：AI时代下什么样的架构更适合？</strong>

<strong>A：我个人觉得一定还是微服务架构，像我这样的单体项目，一方面面对生产实践的时候不能用，另一方面就是微服务架构天生就会对各个功能模块抽离出来，你开发某个特定模块的时候完全不需要考虑另外一个模块的工作原理，只要知道他的输入输出格式就可以，天生适合用AI去做开发，当一个模块出bug或者需要大改的时候，一方面不需要整个项目完整发给AI，项目结构也比较清晰易于改动。</strong>

## 总结

本课程设计完成了一个围绕行情展示与模拟交易 Agent 的鸿蒙移动端应用。项目包含登录认证、首页、行情页、搜索页、股票详情页、Trade Agent 页面、我的页、交易记录页、Java 业务后端、Python Agent 后端、MySQL、Redis、SSE 流式通信和大模型总结等内容。

从技术层面看，本项目的重点不只是完成页面展示，而是通过 Java + Python 双后端分工，让普通业务和 Agent 流式任务分别由更合适的技术实现。Java 后端负责稳定业务、登录认证和数据持久化；Python 后端负责模拟行情、策略分析、大模型总结和 SSE 推送；鸿蒙前端负责页面展示、状态管理和用户交互。

从工程层面看，本项目让我认识到，一个 App 的开发应该先有选题和功能树，再有页面草图和导航结构，然后通过小 Demo 验证技术难点，最后逐步组合成正式项目。AI 可以提高开发效率，但必须在明确边界内使用，不能让 AI workflow 黑盒式地主导整个项目。

我不能说这个项目做得多好多好，其实负责任的说，这个项目存在很多潜在的业务风险，有很多安全漏洞，但是这个项目于我的价值并非是开发一个app这么简单，而是让我真正了解了AI时代的全新的开发范式，自己去摸索出一条更适合AI开发的模式，在项目中学习在项目中成长，我相信尽管这个项目将成为我未来全新项目的一个基石，是全新项目的试错成本。
