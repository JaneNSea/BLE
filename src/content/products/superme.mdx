## 从“展示 Agent”走向“交易可验收的结果”

生成式 AI 让 Agent 快速涌现，但供需之间仍缺少一套真正能完成交易的基础设施：个人和中小企业难以低成本找到可信能力，Agent 开发者的能力缺少持续变现渠道，复杂任务又很难由单个 Agent 独立完成。

SuperMe 的核心判断是：**下一代 Agent 平台不应该只陈列能力或提供聊天窗口，而应该围绕任务契约、协同履约、结果验收、可信结算和信用积累构建。**

## 一条状态机贯通完整履约链路

任务不是一段发出后便失效的 Prompt，而是一份包含目标、预算、期限、验收标准与版本信息的契约。平台用显式状态机约束每次转换，避免审核、交付、退款和争议处理在并发环境中彼此污染。

与一次性对话相比，这套模型把“谁来做、做到什么程度、如何证明做对、失败后如何处理”变成了可审计的工程对象。

## 多 Agent：不是简单串联，而是受约束的动态协作

复杂工程任务会进入中央集群节点，由中央 Agent 判断任务难度、招募候选 Agent、组织互评与挑战，再按预算分配子任务。异构边缘 Agent 可以使用不同模型与工具，但必须遵守任务合同、传播深度和角色约束。

这里刻意避免让中央节点无限感知或控制全部 Agent：参与者通过明确消息与结果协议协作，决策者、评委、挑战者和能力 Agent 具有不同权限，传播深度也受到限制。这使协同过程更容易复盘，也为故障迁移和恶意输出隔离留下空间。

## 可信交易：先建立约束，再谈自动结算

Agent 服务的风险不仅来自支付，还来自重复请求、过期结果、越权调用、交付物被替换以及部分成功。SuperMe 采用类托管结算模型，将额度预冻结、交付验收、分账与退款纳入同一条状态链。

<CaseImage
  src="/images/products/surperme/trusted-transaction.png"
  alt="SuperMe 安全与可信交易模型，展示任务状态机、幂等、事务 Outbox、复式记账和哈希链审计"
  label="Trusted transaction"
  caption="可信交易设计图：全局幂等号、风险权限隔离、事务 Outbox、复式记账与哈希链共同构成可追溯边界。"
/>

下面是用于说明设计意图的脱敏伪代码，不是闭源仓库的生产源码：

```java
// 示意：一次结算必须同时满足状态、证据、幂等与账务守恒
@Transactional
settle(command) {
    order = orders.lock(command.orderId)
    require(order.state == ACCEPTED)
    require(evidence.verify(command.deliveryManifest))

    idempotency.runOnce(command.requestId, () -> {
        wallet.releaseFrozen(order.buyer, order.amount)
        ledger.appendDebit(order.buyer, order.amount)
        ledger.appendCredit(order.agent, agentShare(order.amount))
        ledger.appendCredit(platform, platformShare(order.amount))
        require(ledger.sum(command.requestId) == 0)

        audit.appendHashChained(order.snapshot())
        outbox.save(new SettlementCompleted(order.id))
        order.transitionTo(SETTLED)
    })
}
```

底层设计基于 openGauss 的事务、MVCC 与行级锁；Redis 只承担短期幂等和协调，不作为权威余额数据源。异常通过 Outbox 重投、对账任务和补偿队列收敛，而不是依赖“多重试几次”。

## 架构演进：MVP 控制复杂度，目标架构承接增长

当前 Backend MVP 采用模块化单体：用户、任务、Agent、订单、积分、文件和系统模块由一个 Spring Boot 进程聚合，跨模块只依赖 Facade 接口。这让团队可以先验证产品闭环，不必提前承担完整微服务治理成本。

## 企业解决方案：OpenHarmony Issue 协作

面向企业时，SuperMe 提供的不是通用聊天机器人，而是可插入现有研发流程的任务履约能力。以 OpenHarmony Issue 为例，企业在隔离虚拟机中保留代码仓和执行权，平台负责解析需求、编排云端专家 Agent、审核方案并返回结果。

  src="/images/products/surperme/openharmony-solution.png"
  alt="面向企业侧的 OpenHarmony Issue 解决方案，展示平台编排专家 Agent 并在隔离虚拟机执行验证"
  label="Enterprise solution"
  caption="OpenHarmony 场景设计：云端 Agent 负责深度推理与方案生成，企业侧轻量 Agent 只负责审核和隔离执行，降低代码与环境暴露风险。该方案将由独立项目仓库承载。"
/>

这一方案把权限边界放在第一位：云端 Agent 不直接接触企业代码仓和生产凭据，虚拟机侧 Agent 仅执行受限操作并返回结构化证据。适合从编译失败、依赖异常、特定模块修改和测试定位等结果可验证的任务切入。

## 仓颉自研网关：为高并发 Agent 接入预留内核

随着 Agent 调用从“用户偶尔点击”变成机器间高频请求，网关需要同时处理连接规模、插件扩展、签名鉴权、动态路由与可观测性。SuperMe 设计了一套基于 Cangjie 的全异步非阻塞网关内核，以 Epoll/Kqueue 事件驱动模型结合协程调度承载高并发 I/O。

责任链把限流、鉴权、签名校验、黑白名单、日志和熔断拆成独立插件；路由表支持热更新，让治理策略不必与业务服务同时发布。这里的价值不是“为了自研而自研”，而是探索更适合 Agent 高频接入与鸿蒙生态的安全网关边界。
