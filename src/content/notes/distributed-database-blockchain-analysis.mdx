## 摘要 Abstract

分布式数据库和区块链看似服务于不同目标：前者追求高吞吐、低延迟、强事务语义与可运维性，后者强调多主体环境下的去中心化信任、可验证日志和抗篡改性。但从系统结构看，二者共享一组核心问题：如何在多副本之间形成全序或偏序日志，如何在故障甚至拜占庭故障下维持状态机复制，如何处理跨分片或跨节点事务，以及如何在性能、信任、隐私和治理之间做取舍。

本文以“数据库视角理解区块链、以区块链视角重估数据库”为主线，梳理二者在复制、共识、事务处理、数据可验证性和工程部署上的联系；总结 Spanner、Calvin、PBFT、Bitcoin、Hyperledger Fabric、NeuChain、SQL Ledger、Oracle Blockchain Tables 等代表性成果；列出该方向的前沿研究人员、学校与公司；并指出当前主要问题，包括可扩展性与确定性排序冲突、跨分片原子性、隐私与审计张力、智能合约与数据库事务模型错位、基准评价不统一、去中心化治理成本等。

本文认为，未来更有价值的方向不是简单把数据库“上链”，也不是把区块链当作低效数据库，而是构建面向多主体可信协作的“可验证数据系统”：在可信边界清晰的场景中保留数据库的事务与查询能力，在信任边界不清晰的场景中引入可验证日志、BFT、TEE、零知识证明等机制。

**关键词 Keywords**：分布式数据库；区块链；复制状态机；共识；事务处理；可信数据管理

## 1. 引言

分布式数据库（distributed database）和区块链（blockchain）都试图回答同一个底层问题：当数据和计算分布在多个节点上时，系统如何形成一致、可恢复、可验证的状态。

传统分布式数据库通常假设系统属于一个组织或可信运维域，节点可能宕机、网络可能分区，但恶意行为不是默认威胁模型；因此它重点优化 ACID 事务、复制、分区容错、查询优化和可运维性。区块链则通常假设参与方之间缺乏完全信任，甚至存在拜占庭节点；因此它以密码学、共识、不可篡改日志和激励机制来建立“弱信任环境下的共同账本”。

这种差异导致了二者在工程表现上的强烈反差。Spanner 将 TrueTime 与 Paxos 结合，在全球范围内支持外部一致事务（参考文献 1）；Calvin 用预排序和确定性执行降低分布式事务的协调成本（参考文献 2）。Bitcoin 则用工作量证明、最长链和 UTXO 模型解决开放网络中的双花问题（参考文献 4）；PBFT 及其后续 BFT 协议为联盟链和许可链提供了更强的确定性最终性（参考文献 3）。Hyperledger Fabric 进一步把企业区块链拆成背书、排序和验证三阶段（参考文献 5、6），使其更接近数据库系统的模块化思路。

因此，分布式数据库与区块链不是两个完全割裂的技术栈，而是同一组分布式系统问题在不同信任假设下的两类解法。本文关注的不是泛泛介绍区块链，而是分析二者在“数据管理”层面的关系：区块链何时可以视为一种特殊的分布式数据库？数据库何时需要吸收区块链的可验证和多主体信任机制？

## 2. 核心联系：共同问题与不同信任假设

### 2.1 共同抽象：复制状态机和不可逆日志

复制状态机（State Machine Replication，SMR）是理解二者的关键。分布式数据库的复制日志、WAL、Raft/Paxos 日志，本质上都在记录状态转移；区块链中的区块链表、交易序列、Merkle 根，也是在记录可重放的状态转移。区别在于，数据库日志通常服务于恢复和复制，区块链日志还服务于跨组织审计、不可抵赖和公开验证。

#### 共同抽象：排序日志驱动确定性状态转移

**客户端请求 → 全序/偏序日志 → 确定性执行 → 副本状态一致**

- 数据库侧：WAL、Raft、Paxos。
- 区块链侧：区块、Merkle 证明、BFT。

### 2.2 关键差异：信任、开放性与成本

传统数据库的信任边界一般由组织、账号、权限和运维流程定义；区块链的信任边界则嵌入协议本身。数据库可以把安全问题外包给访问控制、备份、审计和法律责任；区块链则尝试在协议层让不完全可信参与方共同维护一个可验证状态。

#### 分布式数据库与区块链的比较

| 维度 | 分布式数据库 | 区块链 / 分布式账本 |
|---|---|---|
| 默认信任模型 | 单组织或可信运维域，主要容忍崩溃故障 | 多主体、弱信任或无信任，需考虑拜占庭行为 |
| 一致性目标 | 线性一致、外部一致、快照隔离、串行化等 | 共识最终性、链上状态一致、抗双花 |
| 核心日志 | WAL、复制日志、事务日志 | 区块、交易序列、Merkle 证明 |
| 性能目标 | 高吞吐、低延迟、复杂查询与事务 | 可验证、抗篡改、去中心化，吞吐通常次要 |
| 治理方式 | 数据库管理员、云厂商、组织制度 | 协议规则、节点治理、链上 / 链下治理 |
| 适用场景 | 单组织数据管理、在线交易、分析查询 | 跨组织结算、供应链追溯、审计、数字资产 |

## 3. 主要理论基础

### 3.1 一致性、复制与共识

分布式数据库中的一致性可从数据对象、事务隔离和全局时间三个层次理解。Spanner 的代表性贡献是把 TrueTime 暴露给事务协议，从而在全球复制场景中支持外部一致性（参考文献 1）。区块链中的一致性更强调多节点对交易顺序和账本状态的共识：PoW 链通常提供概率最终性，PBFT 类联盟链通常提供确定性最终性（参考文献 3）。

这说明二者的“共识”对象并不完全相同。数据库共识常用于选主、复制日志或分片元数据；区块链共识直接决定外部可见的账本历史。数据库可以在可信运维域内用较低成本获得高性能，而区块链必须为抗作恶支付更多通信、验证和治理成本。

### 3.2 事务处理与确定性执行

Calvin 提出预排序事务并确定性执行，从而减少传统两阶段提交在高争用分布式事务中的协调成本（参考文献 2）。这一思想后来与许可链系统发生了直接联系。NeuChain 明确受到确定性数据库启发，尝试通过确定性事务处理减少显式排序开销（参考文献 7）。Lai 等人的工作也系统讨论了私有链与确定性数据库之间的联系（参考文献 8）。

关键观点是：区块链不是必须永远采用“先共识排序、再串行执行”的低效模式。如果智能合约或交易可以被静态分析、分区、预声明读写集或转化为确定性执行，则可以借鉴数据库的并发控制、批处理、分片和预执行技术。

### 3.3 可验证数据结构与审计

数据库通常通过权限、审计日志、备份和外部监管保证可信；区块链则通过哈希链、Merkle 树、数字签名和共识结果让数据篡改可被发现。

近年来，数据库厂商也开始把区块链式技术引入传统数据库。例如，Azure SQL Ledger 在关系数据库中提供可加密验证的数据完整性（参考文献 11）；Oracle Blockchain Tables 使用插入式、哈希链式表结构来检测行级篡改（参考文献 12）。

这表明“区块链化”不一定意味着去中心化网络。很多企业场景真正需要的是可验证、可审计、不可轻易篡改的数据管理，而不是完全开放的公链协议。

## 4. 代表性系统与成果

### 4.1 数据库侧成果

- **Spanner**：证明全球分布式数据库可以在工程上同时支持同步复制、分布式事务和外部一致性，其代价是复杂的时间基础设施与系统工程（参考文献 1）。
- **Calvin**：以确定性排序和执行降低分布式事务协调成本，为后续“数据库化区块链”提供重要思想基础（参考文献 2）。
- **SQL Ledger / Oracle Blockchain Tables**：将区块链中的哈希链、可验证日志、不可篡改语义移植到成熟关系数据库中，强调审计与合规场景（参考文献 11、12）。

### 4.2 区块链侧成果

- **Bitcoin**：以 PoW 和最长链共识在开放网络中解决双花问题，奠定了区块链作为“公开可验证账本”的基本模式（参考文献 4）。
- **PBFT 与许可链 BFT**：PBFT 展示了实用拜占庭容错复制的可能性，后续成为许多许可链和联盟链的理论基础（参考文献 3）。
- **Hyperledger Fabric**：通过执行—排序—验证架构、背书策略、通道和成员服务，使企业区块链更模块化，也更接近数据库事务流水线（参考文献 5、6）。
- **NeuChain 与确定性区块链**：将确定性数据库技术引入许可链，代表“用数据库技术重构区块链事务处理”的方向（参考文献 7）。

#### Hyperledger Fabric 的执行—排序—验证流程

**客户端提案 → 背书执行 → 排序服务 → 验证读写集 → 提交账本**

| 阶段 | 核心作用 |
|---|---|
| 背书执行 | 并行模拟执行 |
| 排序服务 | 通过共识形成全序 |
| 验证读写集 | 执行 MVCC 与背书检查 |
| 提交账本 | 写入最终账本状态 |

## 6. 当前主要问题

### 6.1 性能与可信之间的根本张力

区块链的安全性来自冗余执行、全网验证、共识通信和密码学证明，但这些机制天然增加延迟和资源消耗。数据库之所以快，是因为它能利用可信边界进行优化，例如中心化调度、权限控制、缓存、索引、查询优化器和低成本复制。

把区块链直接替代数据库，通常会损失吞吐、延迟和查询能力；把数据库直接冒充区块链，又无法解决多主体不信任问题。

### 6.2 跨分片事务与全局原子性

区块链分片被视为解决可扩展性的关键路径，但跨分片事务会重新引入分布式数据库早已面对的难题：两阶段提交、锁等待、死锁、跨分片排序、原子提交和恢复。近期关于区块链分片的综述也强调，跨分片交易处理仍是可扩展性瓶颈（参考文献 10）。

这说明区块链分片不能只讨论节点分组和共识，还必须吸收数据库事务处理理论。

### 6.3 智能合约模型与数据库事务模型错位

智能合约通常以确定性虚拟机和链上状态为核心，强调可重放、可验证；数据库事务强调隔离级别、并发控制、索引访问和复杂查询。

二者结合时常出现三类错位：

1. 合约逻辑不擅长复杂查询。
2. 数据库的非确定性函数、时间、随机数和外部调用不容易上链。
3. 链上全局状态更新不适合高频细粒度 OLTP。

### 6.4 隐私、审计与合规的冲突

区块链的可验证性通常依赖共享日志，但企业数据又要求权限隔离、商业隐私、删除权和合规审计。Fabric 等许可链通过通道和私有数据集缓解问题，但会牺牲全局透明性。零知识证明、TEE 和可验证计算可以补充，但工程复杂度高，且需要新的威胁模型和基准。

### 6.5 基准评价与工程可复现不足

数据库系统有 TPC-C、YCSB 等成熟基准；区块链系统则常使用自定义吞吐、延迟和节点规模指标。不同论文在交易复杂度、合约逻辑、网络延迟、故障模型、硬件配置和确认规则上差异很大，导致系统间难以公平比较。

未来需要“数据库事务 + 区块链信任模型”的统一 benchmark。

### 6.6 治理与升级成本

数据库升级通常由单组织控制；区块链升级涉及多方共识、节点兼容、协议治理和资产安全。对于联盟链，治理成本常常比技术成本更高：谁能修改合约？谁能加入节点？谁承担错误交易责任？这些问题无法只靠共识协议解决。

## 7. 个人思考与总结

我认为，分布式数据库与区块链的关系可以概括为三句话。

第一，**区块链是带有强信任假设修正的分布式数据管理系统**。如果只看数据结构，区块链像追加日志；如果看协议，它像公开或半公开的复制状态机；如果看应用，它是跨组织事实记录系统。因此，区块链研究不能脱离数据库的事务、并发控制、索引、查询优化和恢复理论。

第二，**数据库正在吸收区块链中最有工程价值的部分**。对多数企业而言，真正需要的不是完全去中心化，而是篡改可检测、审计可证明、跨组织可共享的数据记录。SQL Ledger 和 Oracle Blockchain Tables 说明，哈希链、签名和可验证摘要可以作为数据库内生能力，而不是另起一套低效系统。

第三，**未来方向不是“数据库 vs 区块链”，而是“可信数据系统”的分层设计**。我倾向于把系统拆成四层：底层用数据库保证事务和查询性能；日志层提供可验证摘要与历史证明；共识层只在多主体边界上使用，而不是对所有操作全网共识；证明层用 ZK、TEE、签名处理隐私和外部审计。这样既避免区块链过度泛化，也避免数据库忽视跨组织信任。

#### 面向未来的可信数据系统分层思路

1. **应用层**：供应链、金融结算、审计、数据交换。
2. **证明层**：签名、Merkle 证明、零知识证明、TEE 证据。
3. **共识层**：Raft、Paxos、BFT，仅在跨主体信任边界使用。
4. **数据层**：关系数据库、事务、索引、查询优化、恢复。

> 自数据层向应用层，系统以数据库能力提供性能基础；在跨主体协作边界中，通过共识与密码学证明逐步增强可信性。

## 8. 结论

分布式数据库和区块链的联系，核心在于复制状态机、共识日志、事务排序和可验证历史。二者差异，核心在于信任边界和成本函数。数据库更适合高性能、强查询和可运维场景；区块链更适合多主体、弱信任和审计场景。

当前研究前沿正在把二者重新连接：确定性数据库启发区块链排序与执行；区块链的可验证日志被引入关系数据库；BFT、分片、ZK、TEE 和自适应系统共同推动可信数据管理。

对实际科研和工程而言，最重要的判断不是“是否使用区块链”，而是先问：系统中到底哪些参与方互不信任？哪些数据需要第三方验证？哪些操作必须强事务？哪些历史必须不可抵赖？只有把信任边界、事务边界和性能边界同时画清楚，分布式数据库与区块链的结合才不是概念堆砌，而能成为真正可落地的可信数据基础设施。
